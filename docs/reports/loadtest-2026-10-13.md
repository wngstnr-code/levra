# Load test, 13 October 2026 (local fork)

Task BE-54. This is a run of the harness on Dharu's machine against a local Anvil fork. It is **not** the result BE-54 asks for: that run needs staging and the paid RPC provider (BE-15). Read the numbers as a check that the harness works and as early signals, not as capacity.

## How to run

```bash
cd apps/api
MONAD_RPC_URL=http://127.0.0.1:8546 \
DEPLOYMENT_FILE=$PWD/../../contracts/deployments/monad.json \
DATABASE_URL=postgres://levra:levra@localhost:5442/<database> \
USERS=50 DURATION_S=60 THINK_MS=1000 \
WALLETS=<comma separated wallets with positions> OUT=report.json \
npx tsx loadtest/run.ts
```

The harness (`apps/api/loadtest/run.ts`) starts the real API in its own process with the BE-51 limits on, and the KyberSwap budget around the real KyberSwap client. Each virtual user has its own IP address and wallet and sends one request every `THINK_MS`. The mix is 60% `GET /v1/markets`, 25% `GET /v1/accounts/:address`, 15% `POST /v1/quote/open` (change with `MIX_MARKETS`, `MIX_ACCOUNT`, `MIX_QUOTE`). One warm-up request per endpoint runs before the clock starts and is not counted. It reports status codes and p50, p95 and p99 latency per route, the JSON-RPC calls and HTTP requests that left the API, and the KyberSwap calls.

Never point it at a shared public RPC endpoint. Quotes go to the real KyberSwap, but the budget caps them at 30 at once and 60 a minute.

## Setup of this run

- Chain: Anvil fork of Monad mainnet on port 8546, reading state from `rpc2.monad.xyz` on demand. The mainnet deployment (`monad.json`).
- Database: a copy of `levra_staging` with the current migrations, deleted afterwards.
- Wallets: the deployer wallet (one open QQQ long), all other users random wallets with no position.

## Results

| | 50 users, 60 s | 200 users, 120 s |
|---|---|---|
| API requests per second | 29.6 | 6.6 |
| `GET /v1/markets` | 1,083 × 200; p50 3 ms, p95 58 ms, p99 9.8 s | 401 × 200, 84 × 502; p50 98 ms, p95 42 s |
| `GET /v1/accounts/:address` | 449 × 200; p50 49 ms, p95 20.5 s | 9 × 200, 184 × 502; p50 41 s |
| `POST /v1/quote/open` | 12 × 200, 262 × 429; p50 45 ms | 11 × 429, 110 × 502 |
| JSON-RPC calls per second | 20.6 (0.70 per API request) | 5.0 |
| KyberSwap HTTP calls | 88 in 61 s | 64 in 121 s |

## What this shows

- **Outside calls stay bounded.** At 50 users the API made 0.70 JSON-RPC calls per request, because `/v1/markets` is served from the 1 to 2 second cache. KyberSwap got 88 calls in 61 seconds, inside the budget (30 at once plus 60 a minute). Clients cannot push KyberSwap use above the budget.
- **The KyberSwap budget refuses most quotes at 50 users.** 262 of 274 quotes were answered `RATE_LIMITED` by the budget, not by the per-IP or per-wallet limits. 50 users asking for a quote every 7 seconds is heavy traffic, but the budget is the first limit we hit. The budget (an initial proposal) should be raised once KyberSwap's real limit for a registered client ID is known (BE-04 found no 429 at 33 requests in 18 seconds; the official limit is not published).
- **Account reads cost one chain read per new wallet.** Each wallet's `Lens` read is cached only briefly, so cost grows with distinct wallets, not with requests. The slow p95 here comes mostly from the fork fetching every new account's storage from the public RPC, which a real endpoint does not do. Not verified on a real endpoint yet.
- **At 200 users the fork was the bottleneck,** not the API: JSON-RPC calls fell to 5 a second and reads timed out into `UPSTREAM_ERROR`. The API answered with a clear error, never an approximate number. This run says nothing about API capacity at 200 users.
